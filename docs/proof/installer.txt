7. WHAT THIS PROVES AND WHAT IT DOES NOT
--------------------------------------------------------------------------------
PROVES
  - The installer builds from this tree in ~109 s via `just installer`.
  - The .dmg mounts, verifies its checksums, and installs by drag-copy.
  - The installed app runs with the developer toolchain off PATH and the source
    checkout unreachable: it does not shell out to cargo/brew/pyenv/node and
    opens no file under the checkout (lsof: 0 matches).
  - It reaches an open collection (readyz HTTP 200), not merely a process that
    has not crashed yet.
  - The exam-readiness dialog class and its Rust backend are inside the bundle
    and execute correctly there.

DOES NOT PROVE
  - THIS IS NOT A FRESH MACHINE. It is the build machine with PATH scrubbed and
    one directory denied. Anything the app might still pick up from elsewhere on
    this Mac — /usr/local, /opt/homebrew reached by absolute path, Qt or Python
    caches under ~/Library, or system frameworks that a different clean macOS
    install might lack — remains available and would not be caught. Only a real
    fresh device or a clean VM closes that gap.
  - GATEKEEPER. The app is AD-HOC SIGNED and NOT NOTARIZED. Briefcase said so
    explicitly ("will not run on anyone else's computer") and `spctl -a -vv`
    returns "rejected". A user who downloads this .dmg on another Mac will be
    blocked by Gatekeeper and will need right-click -> Open or to clear the
    com.apple.quarantine attribute. The launches recorded here bypassed that
    entirely by running the binary from a shell. Real distribution needs a
    Developer ID identity (SIGN_IDENTITY env var, consumed by
    qt/tools/build_installer.py get_signing_args()) plus notarization.
  - Nobody clicked Tools -> Exam Readiness. See section 6.
  - Only macOS arm64 was built. Windows and Linux installers were not.

8. INCIDENT DURING TESTING (disclosed in full)
--------------------------------------------------------------------------------
Method A — renaming the checkout out from under the filesystem — is unsafe on
this machine because other work was running concurrently. During the second
Method A run at ~23:08, a concurrent Gradle build for Anki-Android recreated
.../anki-whimsified/Anki-Android/ while the real tree was renamed away, so the
restore step moved the real repo INSIDE that recreated directory, leaving
.../anki-whimsified/anki-whimsified/.

Detected immediately and fully repaired:
  $ mv .../anki-whimsified .../anki-whimsified.WRAPPER
  $ mv .../anki-whimsified.WRAPPER/anki-whimsified .../anki-whimsified
  $ mv .../anki-whimsified.WRAPPER/Anki-Android <scratch>/orphaned-gradle-output-Anki-Android
  $ rmdir .../anki-whimsified.WRAPPER

Post-repair verification:
  $ git status --short

     M Anki-Android/AnkiDroid/src/main/res/menu/deck_picker.xml

No source was lost. The only unexpected entry in git status is web/justfile,

The orphaned directory held only Gradle BUILD OUTPUT (454 files, all under

The Android tree has its own pre-existing build/ and .gradle/, so the only cost
is that the concurrent Gradle run of ~23:05 lost its work and must be re-run.

Method B (sandbox-exec) was adopted for every subsequent run precisely because it
touches nothing on disk.
